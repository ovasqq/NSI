## Задача

**Subgraph Isomorphism / subgraph matching.** Дан маленький размеченный граф-запрос Q и большой размеченный граф данных G. Найти вложения: инъективные f: V(Q) → V(G), сохраняющие метки вершин и рёбра Q (не-индуцированная версия, как в базовой статье).

Классическая схема точных алгоритмов (VF3, GQL, CFL, CECI, QSI, RI, …):

1. **Фильтрация:** для каждой u ∈ Q множество кандидатов C(u) ⊆ V(G) (метка, степень, метки соседей и т.п.).
2. **Порядок φ** вершин Q — в каком порядке их сопоставлять.
3. **Перечисление:** DFS с возвратом. На шаге i для вершины u = φ(i) строятся локальные кандидаты C_M(u) — те v ∈ C(u), что согласованы с уже сопоставленными соседями u. Они перебираются по одному.

Внутри шага 3 кандидаты перебираются в фиксированном порядке (по id). Это и есть место, куда встраивается обучение.

## Базовая статья (её воспроизводим и улучшаем)

**Neural Graph Navigation for Intelligent Subgraph Matching (NeuGN).**
Y. Ying, Y. Dai, W. Li, …, T. Zheng (corresp.), M. Song — Zhejiang University. **AAAI 2026.**

- arXiv: https://arxiv.org/abs/2511.17939
- AAAI: https://ojs.aaai.org/index.php/AAAI/article/view/38654
- Репозиторий авторов: https://github.com/Ying-Yuchen/NeuGN — **кода нет** (на ноябрь 2025: только README и `NeuGN_APPENDIX.pdf`). Всё пишем сами по тексту статьи и приложения.

### Идея NeuGN

Нейросеть **переупорядочивает** локальных кандидатов C_M(u) на каждом шаге перечисления (до глубины ~10), ничего не удаляя. Фильтр, порядок φ и правила отсечения базового алгоритма не меняются.
→ **Полнота сохраняется** (доказательство в приложении A: перестановка — биекция на C_M(u) + отсечение не зависит от порядка соседей-кандидатов).
→ **Дерево поиска то же**, меняется только порядок обхода: выигрыш в скорости *первого* вложения, а не полного перечисления.

### Архитектура

- **QSExtractor (GCN):** эмбеддинг меток вершин Q → слои GCN → max-pooling → вектор h_Q («что ищем»). Один раз на запрос.
- **GGNavigator (Transformer, bidirectional, без causal mask):**
  - Q сериализуется в последовательность вершин вдоль **эйлерова пути** (`networkx.eulerize` дублирует минимум рёбер). Соседние токены = ребро Q, граф восстанавливается без потерь. Вершина может встречаться несколько раз.
  - Токен = эмбеддинг содержимого (**ID вершины G**, или `[Pad]` — не сопоставлена, или `[Cls]` — текущая цель; на все вхождения текущей вершины) + эмбеддинг **номера вершины Q** (циклический сдвиг: i' = (i + r) mod N, N = 64, r случаен) + обычное позиционное (BERT-style).
  - Вход: `[h_Q] [Cls-якорь] токены…`. Выход с якоря: linear (|V(G)| × d) + softmax → распределение по всем вершинам G.
  - При поиске локальные кандидаты сортируются по этой вероятности.
- Обе сети обучаются **совместно**, одной функцией потерь.
- **Трансдуктивность:** таблица эмбеддингов ID вершин и выходной слой привязаны к конкретному G. GCN к G не привязан (видит только Q).

### Обучение (self-supervised, без решателя)

1. Каждую эпоху из **каждой** вершины G — случайное блуждание до 5–19 различных вершин, индуцированный подграф = «запрос» (вложение известно — это сами вершины).
2. Эйлеризация → последовательность, циклический сдвиг номеров.
3. Маскируются k вершин; одна — цель (`[Cls]` во всех её вхождениях), остальные скрытые — `[Pad]`.
4. Потеря: −log P(истинный ID цели).

Гиперпараметры: d = 256; 4 слоя, 8 голов, FFN 1024 (Hamster/LastFM — 2 слоя); Adam, lr 5e-4, экспоненциальный спад γ = 0.999; 1000 эпох; batch 128.

**Не указано в статье — выбрать самим и задокументировать:** k (число масок), число слоёв GCN, подаются ли метки вершин в Transformer, начальная вершина эйлерова пути, точный способ батчинга кандидатов.

### Эксперименты статьи

- Данные (метки = классы вершин): Hamster (2 421 / 16 621 / 16 меток), LastFM (7 624 / 27 806 / 18), WikiCS (11 701 / 215 603 / 10), NELL (65 755 / 125 775 / 105), DBLP (317 080 / 1 049 866 / 15), YouTube (1 134 890 / 2 987 624 / 25).
- Запросы: случайное блуждание, по умолчанию 20 вершин (также 8/16/24/32), поток из 200 запросов; dense = средняя степень ≥ 3, sparse < 3.
- Бейзлайны: QSI, GQL, CFL, VF3, CECI, CaLiG, RLQVO, RSM (реализации из Zhang et al., SIGMOD 2024 survey).
- Метрики: **FMS** (First Match Steps, медиана по запросам) — шаги перечисления до первого вложения; **MPS** — вложений в секунду при бюджете 1 с.
- Результаты: FMS снижается до 98.2% (WikiCS, dense); на крупных запросах эффект растёт (CECI, 32 вершины: 254 460 → 8 079); основной выигрыш на глубинах 0–3; MPS +2…92%.
- Абляции: без GCN FMS растёт в ~3–76 раз; MLP вместо Transformer: +49…497%; случайное блуждание вместо эйлерова пути: +10…146%.

### Слабые места NeuGN (наша мотивация)

1. **Цель обучения — «правдоподобное продолжение»**, а не экономия поиска. Модель не знает, сколько стоит обойти поддерево.
2. **Все обучающие запросы выполнимы** — тупиковых продолжений модель не видит.
3. **Трансдуктивность** — для нового графа переобучение; на больших G таблицы |V(G)| × 256 огромны.
4. При полном перечислении и на невыполнимых запросах выигрыша нет **по построению** (авторы этот режим не измеряли).

## Наши идеи

### Идея 1 (основная): учить порядок по результатам самого поиска

**Теория.** Для кандидата i: pᵢ — вероятность, что в его поддереве есть решение; cᵢ — стоимость обхода поддерева при неудаче. Ожидаемое время до первого решения минимально при сортировке по убыванию **pᵢ / cᵢ** (Simon & Kadane, 1975). Доказательство обменом соседей: «i, затем j» стоит cᵢ + (1 − pᵢ)cⱼ, «j, затем i» стоит cⱼ + (1 − pⱼ)cᵢ, и первое не хуже ⟺ pᵢ/cᵢ ≥ pⱼ/cⱼ. Допущения: независимость поддеревьев, при неудаче поддерево обходится целиком. Это приближение, проверять эмпирически.

**Разметка.**
- Малые запросы (5–15 вершин) вырезаются из G, как в NeuGN, плюс **испорченные** (добавить/удалить ребро, сменить метку), чтобы появились тупики.
- Для каждого — **полный перебор** с бюджетом B узлов. В рекурсии каждый узел возвращает (размер поддерева, есть ли решение); один запуск размечает все узлы.
- Примеры: (Q, M, кандидат v) → (has_solution, log subtree_size) для узлов глубины 1–3. Поддеревья, не уложившиеся в B, — цензурированная метка «> B».
- **Ключевое свойство:** размер поддерева *без решения* не зависит от порядка кандидатов внутри (оно обходится целиком) → метка c стабильна относительно нашей же политики. Зависит от φ и отсечения — они фиксированы.

**Модель.** Тот же вход, что у навигатора NeuGN, но позиции текущей вершины заполнены оцениваемым кандидатом v (одна строка на кандидата, батчем). Две головы:
- p̂ — BCE;
- ĉ — Huber на log-размере **или** классификация по корзинам 1–10, 10–100, …; для «> B» штраф только за недооценку.

Альтернатива/дополнение: **попарная ranking-потеря внутри шага** по истинным pᵢ/cᵢ (или нормировка log c по кандидатам шага). Общий масштаб трудности запроса при этом сокращается, что должно помочь переносу на большие запросы. Дисбаланс (большинство поддеревьев крошечные) — взвешивание/стратификация по корзинам.

Полезные дополнительные признаки: размеры списков кандидатов оставшихся вершин после выбора v; число несопоставленных вершин; позиция вершины в φ; оценка размера дерева по Кнуту (несколько случайных спусков).

### Идея 2: индуктивность

Вместо ID вершины G подавать её **признаки** (метка, степень, гистограмма меток соседей; опционально — эмбеддинги доминирования GNN-PE/LIVE). Выход — оценка (p, c) конкретного кандидата, а не softmax по V(G). Тогда в модели нет параметров, привязанных к G → проверяем обучение на одних графах и тест на других.

### Идея 3 (побочная, дешёвая): бейзлайны без нейросети

Сортировка кандидатов по простым признакам (степень, «запас» по доминированию эмбеддингов o(v) − o(u) из GNN-PE/LIVE, оценка Кнута). Если они дают заметную долю эффекта NeuGN — это само по себе результат; если нет — обоснование для обучаемой модели.

### Чего НЕ делаем и почему

- **Простое «GNN-PE + NeuGN»:** GNN-PE собирает ответ hash-join'ами путей, а не DFS; после фильтра (99%+ отсечения) почти нечего переупорядочивать; инференс Transformer (мс/шаг) дороже целого запроса LIVE (мс на 3.8 млн вершин). Литературы с такой комбинацией не нашли (обзор GNN for Databases, IJCAI 2025, делит гибриды на «фильтр» и «порядок»).
- Не мерить «число узлов при полном переборе» как эффект переупорядочивания кандидатов — оно не меняется по построению (годится только как sanity check).

## План работ

Каждый этап заканчивается проверкой; не переходи дальше, пока проверка не пройдена.

0. **Окружение и данные.** Загрузчики Hamster (KONECT) и LastFM Asia (SNAP) — начинаем только с них (малые |V(G)|). WikiCS/NELL — PyG, позже.
1. **Классический бейзлайн на Python.** Фильтр (LDF + NLF), порядок (GQL- или RI-подобный), DFS-перечислитель с **хуком сортировки кандидатов** и счётчиком шагов. Определение «шага» (= одна попытка расширения (u, v) в Enumerate) зафиксировать в коде и в отчёте.
   *Проверка:* число вложений совпадает с `networkx.algorithms.isomorphism.GraphMatcher(...).subgraph_monomorphisms_iter()` на сотнях малых случаев; перестановка кандидатов не меняет множество вложений.
2. **Генератор запросов** (случайное блуждание, dense/sparse) и протокол замера FMS (медиана) и «шагов до первых k».
3. **Воспроизведение NeuGN** (генератор обучающих примеров, GCN + Transformer, обучение, встраивание до глубины 10).
   *Проверка:* качественно повторить снижение FMS относительно того же Python-бейзлайна на Hamster/LastFM.
4. **Оракульный эксперимент (go/no-go).** На малых запросах посчитать истинные p, c на верхних уровнях и сравнить порядки: бейзлайн / NeuGN / оракул p/c / оракул только p / оракул только 1/c. Если оракул p/c не лучше NeuGN заметно — пересмотреть идею 1 до обучения моделей.
5. **Модель (p, c)** — идея 1: разметка перебором, обучение, сравнение с NeuGN и оракулом.
6. **Индуктивная версия** — идея 2: перенос между графами.
7. Бейзлайны идеи 3; масштабирование на кластер; время (не только шаги).

Предлагаемая структура репозитория:

```

search/          # фильтр, порядок, DFS с хуками, счётчики

models/          # GCN, Transformer-навигатор, головы p/c
train/           # циклы обучения, разметка перебором
experiments/     # скрипты экспериментов, конфиги, результаты
tests/           # сверка с networkx, инварианты
```

## Подводные камни (помни)

- **Время vs шаги.** Python-перебор нельзя честно сравнивать по времени с C++-бейзлайнами; основная метрика — шаги. Для оценки накладных расходов модели отдельно мерить время инференса на шаг.
- **Полнота:** модель только переставляет кандидатов; никакого отсечения по выходу сети. Тест на это обязателен.
- **Воспроизводимость:** фиксировать seed'ы, логировать конфиги; все «не указанные в статье» решения записывать в `DECISIONS.md`.
- **Размер словаря:** таблицы |V(G)| × d для крупных графов (DBLP, YouTube) не влезут — сначала малые графы.
- **Перенос по размеру запроса** (обучение на 5–15 вершинах, тест на 20–32) — главный риск идеи 1, проверять отдельно.
