# Переключение глубоких проверок на WikiCS

## Что проверяет эксперимент

Ранее ручная проверка и проверка одного ребра решили по 109 из 120 валидационных запросов при лимите 10 000 назначений. Они разошлись на шести запросах. В 400 из 404 сохранённых состояний, где ручная проверка упустила доступное отсечение, одно из предложенных рёбер уже давало доказательство. Ночной эксперимент измеряет, может ли дешёвое решение в каждом узле сохранить сильные стороны обоих правил и при этом ускорить поиск. Здесь действует мягкий лимит 0,5 с и 100 000 назначений на запрос. Сравнивать числа решений следует внутри этого запуска.

## Что происходит в узле DFS

1. NeuGN ранжирует на первых десяти уровнях. Глубже кандидаты сохраняют порядок DFS. Все режимы одинаково строят полные домены оставшихся вершин. Пустой домен сразу доказывает тупик.
2. После десяти назначений, если осталось хотя бы две вершины, switch просматривает оставшиеся рёбра Q. Если для каждого ребра (u,v) произведение размеров доменов больше T, поиск продолжается без генерации предложений. У каждого связного фрагмента есть ребро, а все размеры непустых доменов не меньше единицы. Поэтому ни один такой фрагмент не уложился бы в порог.
3. Иначе генератор строит до 12 связных фрагментов размера 2–4. Старое ручное правило предпочитает больше рёбер сверх остова, затем меньшее произведение размеров доменов. Если произведение выбранного фрагмента не больше T, переключатель проверяет его.
4. Иначе он берёт предложенное ребро с минимальным произведением размеров доменов, если оно укладывается в T. Возможна ситуация, когда дешёвое ребро есть в Q, но не вошло в 12 предложений. Тогда switch пропускает проверку. При равенстве произведений порядок определяется номерами вершин.
5. На узел приходится не более одной точной проверки с бюджетом 256 просмотров кандидатов. Ветвь закрывается при полном доказательстве невозможности. При найденном локальном вложении или при исчерпании бюджета глобальный DFS продолжается. T управляет выбором, а 256 ограничивает работу проверяющего. Произведение доменов служит грубой оценкой трудоёмкости.

## Протокол и результаты на диске

Используются файлы queries и SHA-256 модели из исходного серверного прогона WikiCS. Launcher пишет commit, имя GPU и run.log. В protocol.json сохраняются параметры, версия torch и контрольные суммы модели и наборов запросов. Обучения модели нет.

- Размеры 16, 24 и 32, dense/sparse. На размере 10 после десятого назначения уже нет остатка.
- Первые 100 индексов каждой группы пропускаются. Для выбора T используются 100–119. Загрузчик исключает из валидации точные дубликаты тестовых запросов по меткам и списку рёбер. Проверки на изоморфизм при перенумерации нет. Тестовые индексы 120–199 ранее использовались в других экспериментах проекта.
- Калибровка пробует T = 64, 256 и 1024 в два повтора. Выигрывает порог с наибольшим суммарным числом решений, при равенстве — с меньшим суммарным временем, далее с меньшим T. Выбранное значение записывается в calibration.json до теста.
- На 480 тестовых запросах сравниваются forward, manual, edge и switch. Forward использует только пустые домены. Manual всегда выбирает ручной фрагмент, edge — одно предложенное ребро с минимальным произведением. Оба работают на той же глубине, что и switch. Во всех режимах дедлайн включает подготовку запроса и ранжировщика. Длинная операция может слегка выйти за мягкий лимит.
- Каждый из трёх тестовых повторов проходит все группы. Внутри каждого запроса режимы перемешиваются с фиксированным seed. Прогрев использует только валидационные запросы. Без учёта прогрева, при отсутствии дубликатов, протокол предусматривает 720 валидационных и 5760 тестовых попыток. При средней стоимости 0,5 с на попытку это около 54 минут плюс накладные расходы. Фактическое время зависит от доли быстрых решений и нагрузки.
- В validation_1.json, validation_2.json и test_1.json … test_3.json есть отдельная запись на попытку. В summary.csv есть строки по каждой группе и строка all для каждого режима и повтора. После успешного завершения launcher упаковывает каталог в соседний tar.gz. Повторный запуск создаёт новый каталог.

## Что смотреть утром

1. Открыть calibration.json и посмотреть, воспроизводится ли преимущество выбранного порога в обоих повторах.
2. В summary.csv отобрать size=all. Сравнить solved и seconds у switch, manual и forward отдельно по трём повторам. Лучше сохранить число решений manual и сократить время. Выигрыш относительно forward — более строгая цель. median_attempt_ms включает таймауты. median_fms_solved учитывает найденные вложения.
3. common_with_manual — количество запросов, решённых одновременно этим режимом и manual в данном повторе. median_common_ms и p95_common_ms относятся к временам текущего режима на этом пересечении. median_paired_delta_ms — медиана разностей времени текущего режима минус manual для каждого общего запроса. Отрицательное значение означает ускорение. Для forward и switch пересечения могут различаться.
4. Отдельно проверить 32 dense и 32 sparse. По test_N.json сравнить, какие конкретно query (в пределах size/density) switch приобрёл и потерял. Отделить быстрый отказ по бюджету от быстрого нахождения вложения.
5. manual, edge и skip в CSV считают решения переключателя или базовой политики. manual обозначает способ выбора и может вернуть ребро. manual_cuts и edge_cuts — доказанные отсечения соответствующего действия. unknown — исчерпание бюджета. select_seconds включает быстрый предварительный просмотр и генерацию предложений, check_seconds — точную проверку. domain_seconds и rank_seconds вынесены отдельно. Сумма стадий описывает лишь часть полного времени.

## Как запустить на Dexter

После передачи пяти файлов и git pull из корня серверного репозитория выполнить:

```bash
nvidia-smi
printf 'Индекс свободной A100: '
read -r gpu
tmux new-session -d -s "frag-switch-$(date +%H%M%S)" "cd ~/subgraph_isomorphism-git && GPU=$gpu bash experiments/launch_fragment_switch.sh"
```

Для наблюдения выполнить `tmux ls` и `tmux attach -t ИМЯ`. Отсоединиться можно Ctrl+B, затем D. После старта отсоединённой сессии SSH можно закрыть. Вне tmux лог можно читать так:

```bash
run=$(ls -td /raid/ovasqq/neugn-runs/wikics_fragment_switch_*/ | head -1)
tail -f "${run}run.log"
```

Готовность подтверждают строка Finished и архив. Если процесс остановился, traceback находится в run.log. С ноутбука скачать последний завершённый архив:

```bash
host=ovasqq@195.70.199.18
key=~/.ssh/id_ed25519_server
archive=$(ssh -i "$key" "$host" 'ls -t /raid/ovasqq/neugn-runs/wikics_fragment_switch_*.tar.gz | head -1')
[ -n "$archive" ] && scp -i "$key" "$host:$archive" ~/Downloads/
```

Локально выполнен сквозной CPU smoke с тем же серверным checkpoint WikiCS, размером 24 dense/sparse, двумя пороговыми повторами и двумя тестовыми. Такой запуск проверяет прохождение пайплайна. Полный серверный benchmark измерит качество политики.
