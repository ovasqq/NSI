# WikiCS — совместное ранжирование и выбор проверок на всей глубине DFS

План большого прогона для коммита `4a9842a`. Главный вопрос — окупается ли обучаемый выбор проверок, когда ранжировщик и контроллер используют одно состояние и могут работать на всей глубине поиска. Сравниваем время и покрытие с исходным NeuGN, `switch` и фиксированным каскадом проверок.

## Идеи, которые проверяет прогон

1. **Ранжировать только текущий домен.** Домен вершины запроса — множество её допустимых образов в графе данных с учётом уже сделанных назначений. Сначала сохраняем исходный ранг по всем вершинам графа как контроль, затем проверяем ранжирование только кандидатов из домена при тех же весах NeuGN. Отдельные режимы сравнивают ранжирование на первых 10 глубинах и на всей глубине.
2. **Использовать одно скрытое состояние для двух задач.** В новой архитектуре небольшой слой из 24 нейронов с ReLU превращает признаки текущего состояния DFS в вектор. Голова ранжирования использует этот вектор и признаки каждого кандидата. Вторая голова оценивает стоимость возможных проверок. Вектор вычисляется по необходимости и переиспользуется внутри одного состояния, пока домены не изменятся. Обучение идёт на GPU, инференс лёгких голов выполняется на CPU через NumPy.
3. **Дать модели информацию об остаточном графе.** Базовые входы — глубина, размеры доменов, признаки следующей вершины запроса и агрегаты по уже назначенным вершинам. Структурный вариант добавляет признаки рёбер и треугольников среди ещё не назначенных вершин, узких доменов и локальных поддержек в графе данных. Например, для кандидата считаем, сколько его соседей попало в домены ещё не назначенных соседей вершины запроса. Дерево и ансамбль в этом прогоне получают базовые признаки. Полное представление пар «вершина запроса — кандидат» с обменом сообщениями остаётся следующим архитектурным экспериментом.
4. **Научить контроллер выбирать проверку по ожидаемой окупаемости.** Дерево, ансамбль и две лёгкие модели сравнивают оценку стоимости проверок с действием `skip`. Варианты выбора доступны на всех подходящих глубинах, когда после назначения остаются хотя бы две неназначенные вершины. Пустой домен останавливает ветвь сразу. Остальные отсечения происходят по доказательству, выданному точной проверкой. При исчерпании лимита фрагмента DFS может продолжиться.
5. **Выбирать момент проверки по работе внутри поддерева.** Контроллер может запустить проверку сразу, пропустить её или отложить каскад до 64, 128 либо 256 пробных DFS-назначений внутри текущего поддерева. Быстро пройденные поддеревья порога не достигают. Три фиксированные задержки дают контроль для обучаемой. Идея с мини-трансформером для долгих веток остаётся отдельным сравнением из [предыдущего пайплайна](experiments/late_check_pilot.py). В новом прогоне задержкой управляет лёгкая модель.
6. **Переиспользовать состояние проверок между DFS-узлами.** Домены обновляются от родительского состояния после очередного назначения. AC-3 может использовать найденные поддержки, паросочетание — подходящую часть предыдущего назначения. Доказательства конфликтов фрагмента и инъективности кэшируются в пределах запроса. Если доказательство применимо к доменам более раннего состояния, поиск может вернуться сразу на этот уровень. Две абляции измеряют вклад механизмов: `joint_fixed_rebuild` отключает переиспользование поддержек и паросочетания при сохранении инкрементальных доменов, `joint_fixed_no_cache` отключает кэш доказательств и связанные возвраты.

### Какие проверки доступны

| Действие | Что проверяет |
| --- | --- |
| `skip` | Продолжить DFS после обновления доменов |
| `arc` | AC-3. У каждого кандидата должна быть поддержка в домене соседа по каждому оставшемуся ребру запроса |
| `matching` | Можно ли дать всем оставшимся вершинам разные образы из их доменов |
| `both` | AC-3, затем паросочетание |
| `lad`, `lad_alt` | Локальная проверка инъективности для соседей выбранных центров, с двумя наборами центров |
| `edge` | Совместимость на одном ребре с малым произведением размеров доменов |
| `fragment`, `fragment_alt` | Точная проверка первого или второго предложения эвристики. Фрагмент — небольшая часть остаточного запроса |
| `forest` | Выполнимость на остовном лесу остаточного запроса с ослабленным требованием инъективности |
| `triangle_join` | Можно ли собрать вложение треугольника из совместимых пар кандидатов |
| `cascade` | AC-3 → паросочетание → локальный LAD → до двух фрагментов. Останавливается при первом доказанном конфликте |
| `defer_64`, `defer_128`, `defer_256` | Отложить каскад до указанного числа шагов внутри поддерева |

У `switch` свой режим. Он поддерживает домены и с глубины 10 применяет существующую эвристику выбора фрагмента. [Реализация действий](search/joint_checks.py) · [Входы и головы модели](models/joint_dfs.py)

## Что запускаем

**WikiCS**, размеры запросов **10, 16, 24, 32**, по два типа связности генерации (`dense` и `sparse`). Все режимы получают одни и те же тестовые запросы. Существующий чекпоинт WikiCS используется для контрольных вариантов NeuGN и `switch`. Лаунчер сверяет его хеш с протоколом исходного прогона.

| Фаза | На размер и плотность | Всего |
| --- | --- | --- |
| Сбор разметки и обучение | Индексы 0–59 | До 480 запросов после удаления дубликатов |
| Калибровка | Индексы 60–89 | До 240 запросов после удаления дубликатов, один повтор |
| Тест | Индексы 120–199 | 640 запросов, три повтора |

Train и validation очищаются по отпечаткам запросов с приоритетом test → validation → train. Можно передать отдельную тестовую выборку через `--test-query-dir`. По умолчанию это эксперимент на одном графе данных, с отдельными тестовыми запросами к нему.

1. **Собираем разметку.** DFS с доменами идёт без дополнительных проверок и без ограничения по секундам, с лимитом 30 000 назначений на запрос. Берём до трёх состояний с каждой посещённой глубины запроса. Для каждого измеряем стоимость доступных проверок и фиксируем, какие доказали тупик. Выигрыш оцениваем по наблюдавшейся работе DFS под состоянием, складывая время и штраф за шаги. Для отложенной проверки используем приближение по доле пройденных шагов. Незавершённые наблюдения помечаем в разметке. Для ранжирования берём известное вложение из генератора и найденное DFS, если оно есть. Сравниваем кандидата из вложения с максимум четырьмя альтернативами из того же домена. Среди этих альтернатив могут быть другие допустимые продолжения.
2. **Обучаем новые модели.** Две модели с общим состоянием для ранжирования и проверок — базовую и структурную — по шесть эпох, плюс одно дерево и ансамбль из 16 итераций. Исходный NeuGN загружаем из готового чекпоинта. Новая разметка обучает лёгкие политики на собственных признаках DFS, без скрытых состояний старого трансформера.
3. **Калибруем порог вызова.** Для `joint_mlp`, `joint_graph` и `joint_adaptive` сравниваем пороги 0, 0.5 и 1 по шкале выхода модели. Сначала минимизируем число запросов, которые решил фиксированный каскад, а политика потеряла. При равенстве берём вариант с меньшим суммарным временем.
4. **Запускаем тест.** На запрос и режим выделяем 30 000 пробных назначений и 1 секунду, включая подготовку пространства поиска для запроса. Останавливаемся на первом вложении. Трижды повторяем каждый режим и перемешиваем их порядок внутри каждого запроса. Общая подготовка индекса графа измеряется отдельно.

### 18 режимов

| Режим | Что измеряем |
| --- | --- |
| `neugn_original` | Исходный контроль в репозитории: классические NLF/GQL, оценка всех вершин графа на первых 10 глубинах, без дополнительных проверок |
| `neugn` | Тот же ранжировщик и глубина, пространство поиска строится с индексом NLF |

| `switch` | NeuGN на первых 10 глубинах, инкрементальные домены и эвристический выбор фрагмента |
| `joint_rank` | Инкрементальные домены и лёгкое ранжирование на всей глубине |
| `joint_graph_rank` | То же ранжирование с признаками остаточного графа и локальной поддержки |
| `joint_fixed` | Лёгкое ранжирование и немедленный фиксированный каскад |
| `joint_tree` | Лёгкое ранжирование и выбор действия одним деревом |
| `joint_ensemble` | Лёгкое ранжирование и выбор действия ансамблем |
| `joint_mlp` | Базовое общее состояние, ранжирование и выбор немедленной проверки либо пропуска |
| `joint_graph` | Структурное общее состояние, ранжирование и выбор немедленной проверки либо пропуска |
| `joint_adaptive` | Базовое общее состояние, выбор проверки сейчас, пропуска либо отложенного каскада |
| `joint_fixed_64`, `joint_fixed_128`, `joint_fixed_256` | Три режима с лёгким ранжированием и фиксированной задержкой каскада |
| `joint_fixed_rebuild` | Фиксированный каскад без переиспользования поддержек AC-3 и паросочетания |
| `joint_fixed_no_cache` | Фиксированный каскад без кэша доказательств и связанных возвратов |

Glasgow — опциональный внешний контроль через `--glasgow-bin`. В стандартный запуск он не входит. При подключении Glasgow сравнение идёт по общему лимиту времени, лимит шагов на тесте отключается для всех режимов.

## Запуск на сервере

В tmux на сервере, после проверки свободной GPU. Прошлый коммит с кодом уже есть в локальной копии `origin/main`.

```bash
cd ~/subgraph_isomorphism-git
nvidia-smi

GPU_INDEX=2  # поменять на индекс свободной карты
git pull --ff-only origin main &&
GPU="$GPU_INDEX" EXPERIMENT=joint_search bash experiments/launch_late_check.sh \
  --sizes 10 16 24 32 \
  --train-queries 60 --validation-queries 30 \
  --test-offset 120 --queries 80 \
  --budget 30000 --seconds 1 --repeats 3 --epochs 6 \
  --branch-queries 8 --branch-samples 3 --progress
```

По умолчанию лаунчер берёт запросы из `/raid/ovasqq/neugn-runs/wikics_deep_ac3_20261118_140911/queries`, а веса — из `checkpoints/wikics/paper1000_seed0/model.pt`. Создаётся каталог `/raid/ovasqq/neugn-runs/wikics_joint_search_XXXXXXXX` и после успешного завершения архив с `results/` и `run.log`. [Скрипт запуска](experiments/launch_late_check.sh)

**Оценка времени.** Ориентир на A100 — **1–3 часа**, без замера полного профиля. В тесте 34 560 запусков, поэтому при среднем времени 100 мс только замеры займут около 58 минут. Если почти все тестовые запуски упрутся в секунду, на них уйдёт около 9 ч 36 мин плюс накладные расходы. Лимит проверяется во время DFS, и отдельная долгая проверка может его превысить. Сбор разметки и обучение идут отдельно. Для быстрого пилота `--repeats 1` сокращает тестовую часть втрое. Локально все 18 режимов уже прошли четыре тестовых запроса WikiCS размеров 10 и 32 с лимитом 1 000 шагов; исходный и индексированный NeuGN совпали на них по факту решения, FMS и числу шагов.

## Как читать результаты

- **Покрытие.** Сколько запросов решили за лимиты. В парном сравнении отдельно считаем общие решения, найденные только одним режимом и не найденные обоими. Последняя группа включает исчерпание лимитов, поэтому по ней нельзя заключить, что задача не имеет решения.
- **Время.** Для каждого запроса берём медиану по повторам, затем считаем медиану и сумму по запросам. В парных таблицах показываем время обоих режимов на одном и том же подмножестве общих решённых задач. Отрицательная медиана разности «режим минус контроль» означает выигрыш сравниваемого режима на этом подмножестве. Классификация по решённости и FMS в сводке берутся из первого повтора, покрытие всех повторов сохраняется отдельно.
- **FMS и стоимость этапов.** FMS — число DFS-шагов до первого вложения. Смотрим медиану FMS на решённых запросах, общее число шагов и время на подготовку, состояние, ранжирование, выбор и выполнение проверок. Счётчики отсечений, срабатываний кэша и возвратов помогают объяснить разницу во времени.
- **Ключевые сравнения.** `neugn_original → neugn → neugn_domain → neugn_full_domain` показывает влияние индекса, доменного ранжирования и глубины. `joint_rank → joint_graph_rank` измеряет вклад структурных признаков в ранжирование. `joint_graph_rank → joint_graph` показывает, что меняется при включении структурной политики проверок. `joint_fixed → joint_tree / joint_ensemble / joint_mlp` проверяет ценность обучаемого выбора, а `joint_adaptive` против `joint_mlp` и трёх задержек — пользу обучаемого момента вызова. Каждый практический выигрыш сверяем с `switch` и исходным NeuGN по времени и покрытию.

| Артефакт в `results/` | Содержимое |
| --- | --- |
| `training_labels.jsonl` | Глубина, работа в поддереве, результаты и время отдельных проверок |
| `joint_models.pt` | Веса двух лёгких моделей, дерево и ансамбль |
| `validation.jsonl`, `calibration.json` | Прогоны на валидации и выбранные пороги |
| `test_records.jsonl` | Все режимы и повторы по каждому тестовому запросу |
| `results.json` | Общая сводка, разбивка по размеру и плотности, парные сравнения, параметры и хеши входов |

## Что проверять следующим прогоном

- Если остаточная структура помогает, дать одинаковые структурные признаки дереву, ансамблю и лёгкой голове. Так можно сравнить архитектуры на одинаковом входе. Затем проверить обмен сообщениями между допустимыми парами «вершина запроса — кандидат» с двумя типами связей: поддержкой рёбер и конкуренцией за один образ.
- Если отложенные проверки окупаются, сравнить лёгкую голову с мини-трансформером на одних и тех же уже долго обходимых поддеревьях. Отдельно измерить время формирования входа и вызова модели.
- Оценить потолок обучаемого выбора на сохранённых состояниях. Повторно пройти каждое состояние с пропуском и с каждой проверкой и сравнить фактическую стоимость. Так можно учесть и проверки, которые сузили домены без немедленного отсечения.
- Для оценки на невыполнимых задачах выделить набор с подтверждённым отсутствием вложения и измерять время до исчерпания поиска. Для проверки переноса использовать новые генераторы запросов и другие графы данных с сопоставимо обученными контрольными моделями.

## Диагностика доказательств и парный тест ветвей

Основной тест сохраняет в `test_records.jsonl` исход каждого повтора: `sat` — найдено вложение, `unsat` — доказано отсутствие, `timeout` и `step_limit` — поиск прерван. Исходы по повторам и группам попадают в `results.json`. Бюджет по времени мягкий. Генератор обычных тестовых запросов сохраняет известное вложение, поэтому отрицательные случаи для анализа берём из ветвей.

- `check_A`, `seconds_A`, `proved_A` — число вызовов действия A, их суммарное время и число доказательств. `cut_R` указывает причину доказательства внутри действия. Например, каскад может завершиться по причине matching. `unknown_A` считает отдельные проверки фрагмента, исчерпавшие бюджет, включая фрагменты каскада. Отсутствующий счётчик в строке равен нулю.
- `direct_cuts` — непосредственные отсечения по пустоте домена, кэшу, немедленной или отложенной проверке. `closed_backjump` отдельно считает подтверждённые закрытия предков после отсечения потомка. Их нельзя складывать как независимые сэкономленные поддеревья.
- `closure_steps_deferred` и `closure_steps_backjump` — сумма фактических попыток назначения между входом в закрытый узел и его закрытием. Деление на соответствующий `closed_*` в одном повторе даёт среднее. У немедленного доказательства число дополнительных попыток равно нулю. `closure_depth_*` — сумма глубин закрытых узлов. `narrowed_A` и `removed_A` — число успешных сужений без немедленного отсечения и число удалённых кандидатных пар.
- После основного теста берутся первые `--branch-queries` запросов из каждой тестовой группы (8 по умолчанию). В каждом идёт отдельный проход `joint_rank` с теми же бюджетами; равновероятная выборка из посещённых префиксов с непустыми доменами и минимум двумя остаточными вершинами даёт до `--branch-samples` ветвей (3 по умолчанию). Выборка описывает посещённые ранжировщиком ветви, может включать вложенные префиксы, а тяжёлые запросы ограничены бюджетом сбора.
- Каждый префикс повторно решают `joint_rank`, `joint_fixed`, `joint_tree`, `joint_ensemble`, `joint_mlp`, `joint_adaptive` с одинаковым базовым ранжировщиком. В начале у каждого пустой кэш и те же исходные домены. Таймер запускается перед обработкой последнего назначения префикса; восстановление общего пути исключено. Счётчик шагов включает только новые назначения ниже префикса. Первая проверка может доказать противоречие за 0 шагов, её время входит в замер. Бюджеты применяются заново для каждого префикса, порядок режимов перемешивается в каждом повторе.
- `branch_trials.jsonl` содержит префикс (образы в порядке GQL), идентификатор запроса и исходы, шаги, секунды и счётчики каждой политики. `branch_summary.json` отдельно по каждому повтору показывает покрытие доказательствами, медиану шагов и времени до доказательства, а также суммарные время и шаги на общих доказанных ветвях против `joint_rank` и `joint_fixed`. Эти суммы служат парному сравнению выборки; экономию всего запроса измеряет основной тест. При параметрах полного запуска возможно до 192 префиксов и 3 456 дополнительных попыток. `--branch-queries 0` отключает эту фазу.

## Пакетная AC-3 при сборе разметки

При разметке `arc`, `both` и `cascade` используют один результат AC-3 на состояние. В метку каждого действия входит одиночная CPU-стоимость AC-3. Последующие этапы каскада измеряются на CPU уже после сужения доменов.

Добавьте к команде совместного эксперимента `--label-ac3 cuda --label-ac3-batch 8 --label-ac3-cpu-stride 8`, чтобы выполнять распространение пакетно на GPU. CUDA-режим измеряет одиночную CPU-проверку примерно на каждом восьмом состоянии в батче и сверяет её результат с GPU. Стоимость остальных состояний оценивается по измерению в том же батче с совпадающим исходом, если такой есть, и близким объёмом доменов на дугах. В `training_labels.jsonl` поле `arc_cpu_measured` отмечает замер. При `--label-ac3 cpu` каждое состояние измеряется один раз.

Это изменение относится к разметке. Валидация и тест по-прежнему выполняют символьные проверки на CPU. CUDA восстанавливает множества из итоговых масок, поэтому порядок перебора кандидатов в последующей бюджетной фрагментной проверке может отличаться. Время всей разметки выводится в `run.log`.

## Дополнительные режимы с замороженным NeuGN

Флаг `--neugn-heads` добавляет три режима к основным 18. Они используют одинаковый NeuGN с доменным выводом логитов и одинаковой глубиной вызова, а домены поддерживаются инкрементально.

| Режим | Политика после обновления доменов |
|---|---|
| `neugn_forward` | Продолжение после проверки непустоты доменов |
| `neugn_head_domains` | MLP с доменными признаками и логитом назначенного кандидата |
| `neugn_head_anchor` | Такая же MLP с дополнительным вектором `anchor` из ранжирования родителя |

Меню обеих голов включает `skip`, `matching`, `lad` и `forest`. Состояния для обучения собираются отдельным обходом `neugn_forward` на train, с одной разметкой для обеих голов. Порог подбирается на validation по потерям относительно `neugn_forward` и суммарному времени. Голова работает на CPU. Полный `anchor` WikiCS (256 чисел) передаётся вместе с логитами одним копированием. Если родитель не вызывал NeuGN, вход головы получает нулевой вектор и признак отсутствия контекста. Правила кэша доказательств у `joint_*` в этой абляции не применяются.

Режимы выводятся в основные записи и сводку. `paired_neugn_heads_vs_forward` измеряет эффект каждой головы, `paired_neugn_anchor` — добавление контекста NeuGN. `rank_context_seconds` и `anchor_decisions` показывают стоимость подготовки контекста и число решений с доступным `anchor`. Отдельный тест префиксов сохраняет исходный набор политик.
