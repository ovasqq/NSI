# Стоимость решения о проверке в одном узле DFS

Первая проверка из [плана](CHECK_TRANSFORMER_PLAN.md). В каждом замере batch size равен 1. Отсчёт начинается с уже построенных доменов, заканчивается, когда код поиска на CPU получил ответ. Случайные веса нужны для измерения стоимости. Во время сбора трасс поиском управляет прежний switch с T=256.

## Какие состояния сравниваются

Граф WikiCS, серверный checkpoint NeuGN, первые 20 обучающих запросов каждой группы 16/24/32 dense/sparse. NeuGN ранжирует до глубины 10. После назначения строятся домены; в выборку попадают вызовы switch при глубине от 10 и хотя бы двух оставшихся вершинах, включая случаи последующего skip. Из каждого запроса берётся равномерная выборка до 12 состояний с помощью reservoir sampling. В трассе используются 100 000 шагов и мягкий лимит 0,5 с от входа в перечисление. Этот лимит управляет сбором примеров, а микрозамеры проводятся после завершения трассы. Все реализации оцениваются на одних и тех же доменах, одним процессом и с одним потоком PyTorch на CPU.

| Реализация | Что входит в время |
|---|---|
| switch на CPU | Текущий выбор из предложенных фрагментов и одна точная проверка, если фрагмент выбран |
| MLP на CPU и GPU | Подготовка семи чисел: глубина, число остаточных вершин и рёбер, минимальная, средняя и максимальная ширина домена, минимальное произведение ширин на ребре. Затем log1p, сеть 7→32→1 и получение решения |
| Transformer ширины 32 или 64 на CPU и GPU | Токен на вершину (метка, log1p ширины, числа назначенных и свободных соседей), токен CHECK, два слоя с четырьмя головами. Вершина видит себя, соседей и CHECK; CHECK видит всех. После последнего слоя скалярное решение возвращается на CPU |

Голова и switch измеряются отдельно. Если обученная голова в будущем скажет «проверить», к её цене добавится цена switch. Ранний NeuGN и построение доменов одинаковы у вариантов и находятся за границей замера.

## Серверный запуск

После git pull из корня репозитория посмотреть nvidia-smi, выбрать свободную A100 и запустить в tmux:
```bash
GPU=2 bash experiments/launch_check_latency.sh
```
Заменить 2 текущим физическим индексом. Launcher сверяет SHA-256 модели с исходным протоколом WikiCS, выбирает GPU по UUID и запускает CPU и CUDA вместе. В конце печатается путь к архиву в /raid/ovasqq/neugn-runs. Параметры микробенчмарка можно передавать в конце команды, например --queries 2 --samples 4 --repeats 3 для короткой проверки.

## Как читать результат

- summary.csv — среднее, медиана и p95 полной задержки в микросекундах, по всем узлам и по числу оставшихся вершин. ratio_to_switch сравнивает средние на одной выборке. Вес каждого состояния равен числу подходящих посещений его запроса, делённому на число сохранённых примеров.
- states.csv — глубина восстанавливается как size минус residual. Для каждого метода записаны все пять полных замеров и их среднее. Перед первым измерением каждого сочетания метода и длины выполняется прогрев. Порядок методов в каждом повторе перемешан.
- Стадии prepare, transfer, forward и return оцениваются отдельным диагностическим вызовом на каждом состоянии. На GPU между стадиями выполняется синхронизация. Поэтому прямая полная задержка измеряется отдельно и служит основной метрикой. Для switch отдельно записаны select и check.
- traces.json хранит запросы, число посещений и префиксы отображения в порядке DFS. protocol.json содержит параметры, контрольные суммы источников, версию torch и устройство. При повторном сборе список состояний может меняться из-за дедлайна.

Если среднее время модели выше полной цены switch на той же трассе, даже пропуск всех проверок не окупил бы её прямую стоимость при вызове в каждом таком узле. Меньшее время оставляет возможность экономии; её величина зависит от того, какие проверки модель сумеет пропустить и сколько нужных отсечений сохранит.
